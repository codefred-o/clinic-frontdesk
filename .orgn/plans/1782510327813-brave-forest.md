## Work Objectives

### Core Objective
Make the existing demo bot reviewable and testable as a lean sales-demo backend, then produce an evidence-based readiness verdict. The executor should prioritize testability and basic demo safety, not production-grade calendar, CRM, database, or human handoff infrastructure.

### Concrete Deliverables
- Fix the current test collection failure.
- Fix the `.env.example` typo.
- Add a small set of targeted tests around core demo behavior.
- Run and report lint/tests.
- Produce a short readiness/code-review summary in the final response.

### Definition of Done
- [ ] `.venv/bin/pytest` passes from the repository root.
- [ ] `.venv/bin/ruff check .` passes from the repository root.
- [ ] Core demo behavior has basic automated coverage without broad production scope creep.
- [ ] Final response states whether the feature is complete/testable and lists remaining demo risks.

### Must Have
- Preserve the existing architecture: WhatsApp webhook → conversation store → LLM → WhatsApp sender.
- Keep booking confirmations fake; do not add real calendar integration.
- Keep test additions lean and focused on the simple demo flows.
- Protect the clinic prompt/profile facts that are central to the sales demo.

### Must NOT Have (Guardrails)
- Do not build real calendar scheduling, persistent storage, CRM, or staff dashboard.
- Do not add broad e2e infrastructure or excessive test cases.
- Do not rewrite the app structure unless a narrow fix requires it.
- Do not commit, push, rebase, or delete branches unless separately requested.
- Do not inspect `.env` secrets; use `.env.example` only.
